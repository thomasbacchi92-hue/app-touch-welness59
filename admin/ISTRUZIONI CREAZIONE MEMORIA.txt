# 🗺️ MAPPA DEL SISTEMA: TOUCH WELNESS ADMIN MASTER

L'architettura attuale è basata sul modello **Master Shell (Guscio Unico)**: esiste un solo file HTML principale che fa da contenitore, all'interno del quale si alternano div nativi e un Iframe per i moduli esterni.

### 1. La Shell Principale (`admin.html`)
È il pilastro della piattaforma. Contiene il menu laterale fisso (`Admin_Menu.js`) e i seguenti moduli nativi:
* **Dashboard (`view-stats`)**: Tabella riassuntiva di tutte le strutture attive.
* **Strutture & Licenze (`view-structures`)**: Creazione di nuove SPA e lista cliccabile.
* **Dettaglio Struttura (`view-structure-detail`)**: Il cuore del gestionale. Suddiviso in 8 Tab (Statistiche, Anagrafica, Personale, Turni, Trattamenti, Magazzino, Licenze/Contratti, Documenti Tablet).
* **Archivio Privacy (`view-privacy`)**: Accesso rapido ai PDF firmati dei clienti salvati su Drive.

### 2. Moduli Esterni (Caricati tramite Iframe invisibile)
Questi file sono indipendenti, ma si spogliano del loro menu originario per fondersi nel guscio principale:
* `admin_crm.html`: Profilazione dettagliata dei clienti, storico trattamenti globale e gestione privacy.
* `admin_customers.html`: Elenco globale dei clienti di tutto il network.
* `admin_chat.html`: Messaggistica in tempo reale con le strutture (testo e vocali audio).
* `admin_magazzino.html`: Hub logistico centrale. Catalogo master, giacenza reale master, carrello per spedizioni alle SPA e registro movimenti.
* `admin_trattamenti.html`: Archivio globale delle tecniche massaggio (con importazione listino predefinito).
* `admin_staff.html`: Creazione e gestione collaboratori, organizzati per "cartelle", con definizione provvigioni, permessi e leve di sconto.
* `admin_documenti.html`: Creazione modelli testuali vergini (con marcatori autocompilanti come `{{NOME_STRUTTURA}}`), archivio file generati e impostazioni cartella Google Drive.
* `Admin_Templates.html`: Set di template di testo per invio automatico WhatsApp.
* `admin_opzioni.html`: Impostazioni estetiche (Tema Notte Premium / Tema Giorno).
* `admin_turni.html`: Generatore di planning settimanale (con funzione di Auto-Pilota AI in base alle preferenze).

# 🔄 COLLEGAMENTI: DA ADMIN AD ADMIN
Il motore di navigazione è gestito interamente da `Admin_Core.js`.

* **Navigazione Nativa (`app.switchView`)**: Nasconde l'Iframe, mostra il div corrispondente. 
* **Navigazione Modulare (`app.loadModule`)**: Nasconde i div nativi, inietta l'URL del file esterno nell'Iframe principale aggiungendo il parametro `?mode=shell`.
* **Navigazione a Tab (`app.openIframeTab`)**: Inietta un file esterno (es. i Turni o lo Staff) direttamente dentro una sottoscheda del Dettaglio Struttura, passando il parametro `?mode=tab`.
* **Comunicazione Bottom-Up (`window.parent`)**: I file esterni (Iframe) comandano il guscio padre. Ad esempio, quando premi "Torna alla Dashboard" dentro la Chat, il comando eseguito è `window.parent.app.switchView('stats')`.

# 🗄️ COLLEGAMENTI: DA ADMIN A DATABASE (FIREBASE)
Il sistema legge e scrive nel nodo radice `MASTER_ADMIN_DB`.

* **`structures/`**: Anagrafiche base, stato archiviazione e scadenza licenza.
* **`users/`**: Anagrafiche collaboratori, credenziali, `commissions` (provvigioni), `levers` (sconti/budget max) e `permissions` (sblocco cassa/turni).
* **`global_customers/`**: CRM universale.
* **`global_treatments/`**: Listino Master da cui le SPA possono attingere.
* **`magazzino_master/`**: `catalogo` (anagrafica materiali), `giacenze` (stock fisico dell'hub) e `logs` (storico carichi/scarichi e spedizioni).
* **`structures_data/{id}/`** (I dati isolati di ogni singola SPA):
    * `info`: Dati fiscali e legali.
    * `settings/active_docs`: Array dei moduli privacy attivi per il tablet.
    * `app`: Storico appuntamenti per calcolo incassi e statistiche.
    * `turni`: Planning settimana.
    * `servizi`: Tecniche importate dal Master e abilitate nella specifica SPA.
    * `products` / `in_transit`: Logistica e pacchi in arrivo.
    * `contracts`: Documenti PDF (o generati testualmente) intestati alla SPA.
* **STORAGE (File Multimediali)**:
    * `chats/{struttura}/...`: File `.webm` per i messaggi vocali.
    * `contratti/{struttura}/...`: File PDF dei contratti di affiliazione/assunzione.

# 📱 COLLEGAMENTI: DA ADMIN A CLIENT SPA / RECEPTION
La genialità tecnica del sistema è che **Admin non parla mai direttamente con l'App**. Admin altera i nodi Firebase, e i Client (in ascolto perenne) reagiscono istantaneamente:

1.  **Firma Tablet (Privacy)**: Admin inserisce un modulo negli `active_docs`. Il Tablet intercetta la modifica e attiva il popup col Canvas (Firma Elettronica) la prossima volta che il cliente entra.
2.  **Autorizzazioni di Cassa (Reception)**: Admin imposta i limiti su `levers.max_perc` e `permissions.auth_annulla_cassa`. Quando il manager usa il PC, i tasti per riaprire giornate fiscali chiuse o fare sconti esagerati spariscono o vengono inibiti se i valori non lo consentono.
3.  **Spedizioni Merce (Reception)**: Admin clicca "Spedisci" nel magazzino. I dati finiscono in `in_transit`. Sul PC della reception compare un avviso rosso. Quando la reception clicca "Accetta", la merce viene spostata automaticamente nello scaffale virtuale della SPA.
4.  **Blocco Agenda (Client SPA)**: Admin genera i Turni con l'Auto-pilota. Il Client legge i turni e impedisce la generazione di appuntamenti al di fuori di quelle fasce orarie.

# 🖥️ STRUTTURA GRAFICA E TECNICA (UI/UX)
* **Gestione Tema**: Uso intensivo di CSS Variables (es. `var(--bg-body)`, `var(--accent)`). La pagina `admin_opzioni.html` scrive `tw_admin_theme` nel `localStorage`. Tutti i file controllano questa variabile all'avvio e, se vale 'light', aggiungono la classe `.light-theme`, invertendo i colori.
* **Modals Unificati**: Le finestre pop-up usano standard rigidi (`.modal-overlay` e `.modal-box`). Non ci sono pop-up brutti nativi di Windows/Mac (nessun `prompt` o `alert` invadente).
* **Progressive Web App (PWA)**: Il `manifest.json` e il file `sw.js` (Service Worker) garantiscono l'installazione del pannello come un'app Desktop/Mobile e il pre-caching della Shell principale.

# 🚨 PUNTI DI CRITICITÀ (RISCHI DI CROLLO DELLA PIATTAFORMA)
In caso di future modifiche o espansioni, questi sono i punti in cui un errore umano (tuo o dell'IA) farebbe implodere il gestionale:

1.  **La Trappola di `window.parent`**: Se in un futuro crei un bottone in `admin_magazzino.html` e gli dici di fare `app.switchView('stats')`, l'interfaccia crasherà. Tutti i moduli dentro l'Iframe **devono** usare `window.parent.app...` per chiamare le funzioni di sistema, poiché il motore JS si trova nel file padre (`admin.html`).
2.  **Scomparsa del parametro `?mode=`**: Se il file `Admin_Core.js` perde le righe che iniettano `?mode=shell` o `?mode=tab` durante i caricamenti, i file Iframe inizieranno a disegnare le proprie Navbar e Sidebar dentro l'Iframe. Si creerebbe un "Effetto Inception" (un menu dentro il menu dentro il menu).
3.  **Aggiornamenti Distruttivi (`.set` vs `.update`)**: Attenzione alle funzioni di salvataggio. Usare `db.child('users/U123').set({ name: 'Mario' })` cancellerebbe del tutto le password, le provvigioni e le leve dell'operatore (perché `set` sovrascrive tutto). Bisogna sempre usare `.update()` per preservare i dati esistenti.
4.  **Dati Orfani**: Attualmente, la cancellazione di una SPA cancella i nodi `structures/{id}` e `structures_data/{id}`. Tuttavia, i collaboratori registrati in quella SPA rimangono nel DB come "Orfani". Il sistema attuale è tollerante (mostra "Nessuna Struttura"), ma modifiche future a cicli `for/each` che si aspettano una struttura valida potrebbero causare errori bloccanti.
5.  **Re-inizializzazione di Firebase**: Tutti i 15 file possiedono il blocco `firebase.initializeApp(...)`. Fortunatamente, è protetto da `if (!firebase.apps.length)`. Se in una modifica questa protezione venisse rimossa, l'Iframe tenterebbe di inizializzare Firebase due volte, causando una schermata bianca (Fatal Error).
